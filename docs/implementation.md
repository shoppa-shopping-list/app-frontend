# Как устроен фронтенд

## Стек и границы модулей

- `app` собирает Redux store, маршруты и жизненный цикл приложения.
- `pages` связывает данные и пользовательские действия на экранах.
- `features/product-editor` отвечает за создание, изменение и удаление продуктов.
- `features/transfers` отвечает за отложенные переносы и отмену.
- `entities/product` содержит типы продукта, выбор видимых продуктов и компоненты строк/палитры.
- `shared` содержит API, Telegram-адаптер, общие настройки и доступную модальную панель.

Это небольшой набор слоёв с направлением зависимостей сверху вниз. ESLint запрещает импорт features/pages из entities и shared. Типы продукта выводятся из OpenAPI: при изменении контракта TypeScript покажет несовместимые места.

React отвечает за интерфейс, React Router — за URL и историю переходов. Экраны редактирования загружаются через динамический `import()` при переходе: они не нужны для первого открытия списка. SCSS Modules изолируют имена классов. Motion удерживает удаляемую строку до завершения exit-анимации и плавно перестраивает список; пользовательская настройка уменьшения движения учитывается.

Radix Dialog управляет фокусом, блокирует фон под панелью и поддерживает Escape. Кнопки имеют доступные названия, а сообщения о переносах озвучиваются через live region. Иконки берутся из Lucide; цветные точки и полупрозрачный след — элементы интерфейса из макета.

## Разделение страницы и логики

`ShoppingPage` собирает экран и хранит поисковый запрос. `ProductSearch` получает значение через `query` и сообщает об изменениях через `onChange`: своего состояния у поля нет. Поэтому при открытии вложенной карточки продукта поиск не сбрасывается. `FrequentProducts` получает продукты, ожидающие переносы и обработчик `onToggle`; компонент отвечает только за отображение и доступность кнопок.

`useShoppingProducts(cart)` объединяет запросы продуктов и корзины, локальные переносы и действия `toggle`/`clearCart`. Это пользовательский React-хук: он связывает существующие хуки и возвращает странице готовые данные и функции. Он не создаёт отдельную копию серверных данных в `useState`, поэтому обновления RTK Query сразу попадают на экран.

`productsWithTransfers()` — чистая функция: её результат зависит только от переданных аргументов, она не отправляет запросов и не меняет Redux. Сначала `visibleProducts()` определяет принадлежность продуктов по серверной корзине, затем локальный перенос временно удерживает строку на исходном экране. `Set.has()` проверяет принадлежность по идентификатору, а `filter()` сохраняет исходный порядок продуктов. Это правило находится в `features/transfers`, потому что обычная сущность продукта не должна зависеть от механизма отмены. Отдельные тесты проверяют обновления корзины во время ожидания/сохранения и удаление продукта другим пользователем.

`useAppLifecycle()` собрал эффекты Telegram и отмену ожидающих переносов при скрытии приложения. Он вызывается в `App` до условных возвратов, поэтому выполняется и на экранах загрузки/авторизации. Возвращаемые из `useEffect` функции снимают обработчики событий при изменении зависимостей или размонтировании; это предотвращает накопление подписок. Таймеры переносов по-прежнему принадлежат Redux listener и не зависят от переходов между страницами.

## Три вида состояния

**Серверное состояние** хранится в RTK Query: продукты и корзина. `createApi()` создаёт кеш и React-хуки, например `useProductsQuery()`. Одинаковые запросы из разных компонентов используют один кеш. `providesTags` помечает данные, `invalidatesTags` сообщает, какие данные перечитать после изменения.

**Локальное состояние** React (`useState`) хранит текст поиска, выбранный цвет и состояние формы. Эти значения не нужно разделять со всем приложением.

**Ожидающие действия** хранятся в отдельном Redux slice. Список на сервере ещё не изменён, но пользователь уже запустил анимацию. Поэтому такие действия нельзя смешивать с серверным кешем.

`visibleProducts()` строит Set идентификаторов корзины и оставляет продукты, принадлежность которых соответствует экрану. Это две проекции одного набора продуктов: перенос не удаляет продукт. `searchProducts()` обрезает пробелы и сравнивает имена без учёта регистра.

## Отмена и таймеры

`transfers.requested()` записывает продукт, направление, время начала и уникальный `token`. `createListenerMiddleware()` слушает это действие вне React-компонентов; переход на другой экран не уничтожает таймер.

После `delay(3000)` listener заново читает Redux. Если token изменился или действие отменено, запрос не отправляется. Проверка token важна для последовательности «тап → отмена → новый тап»: старый таймер не должен выполнить новое действие раньше срока.

В фазе `waiting` повторный тап удаляет ожидающее действие. В фазе `saving` запрос уже отправлен и кнопка временно отключается. После успешного запроса перечитывается корзина. Только затем убирается локальное ожидание, чтобы старый кеш не заставил строку мигнуть обратно. `unwrap()` превращает результат RTK Query в обычный Promise: при ошибке управление попадает в `catch`. `reset()` освобождает запись ручной мутации после завершения.

Если сохранение не подтверждено, показывается ошибка и перечитывается состояние сервера: при обрыве сети сервер мог успеть сохранить запрос. Это не офлайн-очередь. При скрытии приложения ещё не отправленные действия отменяются; отправленные операции завершаются. Полная офлайн-политика остаётся открытым требованием.

При Clear cart запускается отдельный перенос для каждой строки. Можно отменить отдельные продукты. API не предоставляет атомарной очистки корзины; при частичной ошибке сохраняется успешный результат и показывается ошибка для неудавшихся переносов.

## Реальное время и авторизация

`EventSource('/api/events')` открывает один поток на приложение. Бэкенд отправляет только событие `changed`, поэтому клиент не пытается извлечь из него продукт, а инвалидирует кеш списка и корзины.

После открытия/восстановления SSE, возвращения на экран и события online выполняется обновление. Это закрывает пропущенные уведомления. Ошибка SSE также запускает обновление через API, чтобы при истёкшей cookie могла восстановиться сессия. EventSource сам переподключается.

`baseApi` сначала делает обычный запрос с cookie. При 401 получает `Telegram.WebApp.initData` и обменивает его на сессию. Несколько параллельных запросов разделяют один Promise авторизации. InitData не сохраняется в localStorage или Redux. Ошибка обмена возвращается как ошибка загрузки, а не маскируется под отсутствие доступа.

Бэкенд — источник истины. У него нет версий сущностей или compare-and-swap: при одновременных изменениях итог задаёт порядок принятых сервером запросов. Клиентская отмена не пытается откатывать действия другого пользователя.

## Макет и контракт

Сохраняются типографика, размеры, отступы, нейтральные фоны и расположение основных элементов исходного HTML. Осознанные отличия:

- API принимает 10 цветов: red/orange/yellow/green/blue/purple/brown/black/white/none; в макете 8 цветов, включая неподдерживаемые teal/pink/indigo. Палитра использует значения API.
- Продукты отсортированы сервером по цвету, затем по имени; в макете демонстрационный порядок.
- В карточку добавлен пункт Edit name; панель выше исходной на одну строку.
- Постоянное удаление продукта требует подтверждения, чтобы отличаться от обратимого переноса в корзину.
- Длинные имена в строке сокращаются многоточием, полное имя доступно в карточке и доступном названии кнопки.
- Скролл списка, Frequent и формы работает на небольших экранах; содержимое не ограничено жёсткой высотой 844px.

## Проверки качества

TypeScript: strict, noUncheckedIndexedAccess, exactOptionalPropertyTypes, noImplicitOverride. Доступ по индексу может вернуть undefined; optional-поле не равнозначно явно переданному undefined.

ESLint: strictTypeChecked + stylisticTypeChecked, React Hooks, JSX accessibility, import cycles и границы слоёв, корректное использование Promise, правила Vitest и Playwright, обязательное объяснение подавления правил. Исключён только сгенерированный API. Browser-глобалы доступны фронтенду, Node-глобалы — конфигурации и тестовой инфраструктуре.

Stylelint проверяет SCSS; Prettier форматирует. camelCase разрешён для CSS Modules. Модульные тесты проверяют разделение списка и корзины, поиск, состояния отмены и доступность палитры. Playwright работает с реальными API/auth/SSE и независимыми cookie двух пользователей. Telegram SDK подменяется только внутри тестового браузера; production-веток обхода авторизации нет.

Браузерная эмуляция не заменяет проверку реального Telegram WebView, клавиатуры и safe areas на iPhone/Android. Перед публикацией нужна проверка с настоящим ботом и HTTPS.

## Зависимости

Применены доступные совместимые исправления `npm audit`. Остаётся advisory GHSA-vfj7-8cjw-p6xm в dev-зависимости `braces`, которую тянет Stylelint; npm отмечает всю зависимую цепочку. Исправления в npm на момент проверки нет. Эта цепочка не входит в клиентскую production-сборку; ей передаются локальные шаблоны путей из настроек линтера.

На финальной проверке `npm audit --omit=dev` сообщает 0 уязвимостей. Основной JS chunk — около 504 kB (163 kB gzip); Vite выдаёт предупреждение о превышении порога 500 kB. Сборка проходит, формы и панель уже загружаются отдельно; дальнейшее уменьшение начального JS можно выполнить после измерения загрузки на реальном телефоне.
